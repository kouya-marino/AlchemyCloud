# AlchemyCloud code audit — 2026-08-27

**Audited at** `9a8eb16` (v1.2.0) · **remediated by** `a953745..cbcc1c4` (v1.3.0)

## The bottom line

This is well-built software. The separation between the Qt shell and the pure-compute
core is real — the full `load → voxel → SOR → level_ground → build → save` pipeline
runs with PyQt never entering `sys.modules`. The threading model is careful and
correctly reasoned. **The exported map geometry was already correct**, verified by
round-tripping an asymmetric obstacle back out of the PGM, and that is the single
property that matters most.

What let it down was not architecture but **unguarded assumptions about real data**.
Three of the four most serious defects shared one root cause: the code trusted whatever
RANSAC, Open3D, or the user handed it, and never asked whether the answer was plausible.

## The five that mattered most — all FIXED

### 1. "Level Ground" and "Remove Ground" fitted *any* dominant plane
`alchemycloud/pcd_ops.py` · **FIXED** in `7019405`

`segment_plane` returns the plane with the most inliers, and the code aligned it to +Z
unconditionally. On this repo's own room scan a wall wins:

```
ppt_15july.pcd — 2,217,416 pts, true Z extent 1.80 m

run0: normal=[0.990 0.109 0.084]  tilt=85.17°  → Z extent after = 21.55 m
run1: normal=[0.993 0.114 0.029]  tilt=88.37°  → Z extent after = 21.66 m
run2: normal=[0.988 0.112 0.109]  tilt=83.75°  → Z extent after = 21.53 m
```

A ground normal must have `|n_z| ≈ 1`; these are ≈ 0.08. The wall genuinely wins on
inliers — 383,100 points against the floor's 209,849 — so this was the *expected*
outcome, not bad luck. The rotated cloud is what became the occupancy grid.

**Fix:** `fit_ground_plane()` restricts candidates to the lowest `floor_band` (30 %) of
the Z range *and* rejects any fit more than `max_tilt_deg` (30°) from horizontal,
dropping those inliers and retrying. With no near-horizontal plane at all it raises
rather than applying a nonsensical rotation. After: tilt 0.30°, extent 1.98 m.

### 2. A failed save reported success
`alchemycloud/pcd_ops.py:18` · **FIXED** in `7019405`

`save_pcd` discarded the `bool` from `o3d.io.write_point_cloud`, which returns `False`
and logs to stderr rather than raising — and a `gui-scripts` entry point hides stderr
entirely on Windows.

```
save to missing dir : returned normally; file exists=False
save to /proc       : returned normally; file exists=False
```

The status bar said *"Saved to /path/to/file"* either way. Compounded by there being no
dirty tracking and no close prompt, so an editing session could be lost twice over.

### 3. The viewer drew 1,580 of 2.2 million points
`alchemycloud/pcd_ops.py:193` · **FIXED** in `7019405`

`voxel = extent / cbrt(max_points) * 1.5` assumes points fill a cube. A LiDAR floor
scan is a *slab*, so occupancy grows with area and the voxel came out one to two orders
of magnitude too coarse. The correction loop could only decimate further, never recover.
Replaced with uniform random subsampling: hits the budget exactly, O(n), keeps real
source points.

### 4. One NaN or one glitch return broke the pipeline
`alchemycloud/occupancy.py:82,103` · **FIXED** in `7019405`, `48b01db`

```
one NaN point   → ValueError: cannot convert float NaN to integer
                  + the entire cloud renders black (NaN poisons the colormap)
one x=1e9 point → MemoryError: Unable to allocate 1.82 TiB
```

Both are ordinary for raw LiDAR. `load_pcd` now strips non-finite points and reports
the count; the grid builder filters them before indexing; and allocation is capped at
25 M cells, with the error naming stray outliers when they, rather than the scan, are
what inflated the extent.

### 5. CI had never been green
`.github/workflows/` · **FIXED** in `a953745`, `0ed2196`

25 `ruff check` errors and 14 of 17 files failing `ruff format --check`, with `build`
depending on `lint` — so nothing could ship through CI. Separately, `publish.yml`
published on any `v*.*.*` tag with no tests and no tag/version check, and all seven
tags `v0.1.0`–`v1.2.0` point at the same commit, so it had already fired seven times
each trying to upload 1.2.0.

### WON'T FIX

- **Tristate + `voxel3d` quantises Z to voxel centres**, so an obstacle just above the
  threshold can resolve as below it. Now documented as deliberate: a voxel resolves the
  same way its midpoint would, which is the consistent choice for a voxelised method.
- **`Tool` strategy abstraction** to replace the four parallel boolean mode toggles, a
  **`Document` model** to own cloud + path + history, and **command-object undo**. These
  are redesigns, not defects. Every bug they would have prevented is fixed directly; the
  seams are documented for whenever the file sizes justify the churn.

## What was verified correct

A review that only lists defects misrepresents the codebase. Each of these was actively
attacked and held.

- **The exported map geometry is correct.** An asymmetric L-shaped obstacle exported and
  reconstructed from `(pixel, origin, resolution)` recovers `X[1.95, 5.95] Y[0.95, 2.95]`
  against a truth of `X[2, 6] Y[1, 3]`. No transpose, no mirror; the `flipud`/origin
  pairing is right, and it writes genuine P5 binary PGM. *(Now pinned by
  `test_occupancy_geometry.py`, which was the gap: hard-coding the YAML origin to
  (0,0,0) or deleting both vertical flips previously passed the entire suite.)*
- **The ROS threshold constants are the canonical ones.** `UNKNOWN = 205` with
  `free_thresh = 0.196` gives p = 0.196078, clearing the threshold by 7.8 × 10⁻⁵ so
  `map_server` reads it as unknown rather than free. That margin is razor-thin by design
  and was chosen correctly.
- **The projection pipeline is sound under a real camera.** World → screen → world
  round-trips to 0.018 m under an oblique perspective view, points behind the camera are
  correctly culled via `w > 1e-9`, and crop selection is a strict subset of in-front
  points. The suite only ever used an identity MVP, so this was unverified until now.
- **Crop and eraser operate on the full cloud.** The obvious bug — computing a mask from
  the display-LOD subset and applying it to the full cloud — is not present.
- **The marker transform is exact.** `p_local = R(−yaw)·(p − m)` matches an
  independently constructed `Rz(yaw)ᵀ(p − m)` to 4.4 × 10⁻¹⁶.
- **The concurrency model is careful.** Explicit re-entrancy guard, actions disabled
  while busy, `closeEvent` disconnects in-flight worker signals, `setAutoDelete(False)`
  with a comment explaining precisely why, bounded undo, `blockSignals` around spin-box
  range updates. `QAction` slots bind `triggered`, which `setChecked()` does not emit —
  so the recursion this pattern usually causes cannot happen here.
- **Corrupt files are caught at the door.** Open3D silently returns an empty cloud for
  garbage input; `load_pcd` converts that into a real `ValueError`.
- **Japanese file paths work end to end** — `点群データ.pcd`, `3階_地図.ply` and
  `地図_出力.pgm` all save, reload and export correctly.
- **The compute core is Qt-free and NumPy-2 clean**, so batch use is real rather than
  aspirational.

## Method

Seven reviewers worked in parallel over separate dimensions — geometry, occupancy,
viewer, concurrency, state, robustness, hygiene. Each dimension's findings then went to
an independent skeptic instructed to *refute* them, running code wherever a claim could
be settled empirically. Three analysis lenses (architecture, robotics fit,
maintainability) and a completeness critic ran alongside. Fifty raw findings entered
verification; 49 survived and one was refuted; the critic added eight more.

That low refutation rate deserves scepticism, so the consequential claims were
reproduced directly against this repository's own data rather than relayed. That pass
also corrected two conclusions: the crop/eraser mutex was *not* functionally broken (the
viewer enforces it internally — only the button state desynced), and
`display_downsample`'s aliasing was *not* a live bug (its one call site already guards
it). Both were downgraded accordingly.

One finding — the additive GL blend mode — was found afterwards, by a user reporting the
RGB view looked worse than a web viewer. None of the eighteen agents caught it, because
GL blend state is invisible to a test suite whose paints all throw and get swallowed.
That is worth remembering about the PARTIAL entry above.
